基于本地 Docker 部署（llm-router-web + llm-router-server + postgres + redis）的端到端实测审计
审计时间：2026-05-26　|　审计方法：Playwright 浏览器驱动 + curl 直连接口 + 源码交叉核对　|　被测主机：http://localhost
后端版本：migration v22　|　构建 ID：index-Cwve4tjX.js　|　被测账号：weakpw@example.com（普通用户）/ admin@example.com（管理员）

1. 摘要

本次审计在本地真实运行的 LLM Router 平台上完成，覆盖未登录态、用户注册/登录、API Key、Playground、Webhook、DLP、Subscription、Members、Profile，以及管理员后台的 Providers / Audit / Settings / Finance 等模块。同时通过命令行直连验证了 /graphql、/v1/*、/healthz、/metrics 等接口的真实行为。

总体来看，平台的架构与安全基线已经搭起来（HSTS、CSP、frame-ancestors、refresh cookie HttpOnly+Secure、SSRF 拒绝内网主机、GraphQL 关闭 introspection、写时鉴权下沉到 directive 等都已落地）。但在真实可用性、跨模块一致性、UI/UX 闭环层面有大量未收尾的细节：CSP 与 Sentry/Worker 互相打架、相同 Header 被前后两层重复设置且参数不一致、注册流程对密码强度的说法与实际后端校验不一致、错误以「内部错误」吞掉、新建账号自动赠送 5 美元（开放注册下相当于资金漏洞）、Subscription 与 Dashboard 余额两套真相、Onboarding 弹窗每次切页都重新弹出等等。

同时存在 2 个安全敏感发现：访问态 JWT 直接保存在 localStorage 以及 普通用户 UI 主动请求管理员级 GraphQL 字段并将「403 forbidden」原文 toast 给用户。前者使得任意一次 XSS（哪怕只是粘贴一段名字字段绕过）都能导致长期会话窃取；后者会向终端用户暴露后台权限模型与字段名。

2. Critical 严重问题

Critical C-01　开放注册 + 自动赠送 $5 余额 + 无人机校验 = 资金可批量套取 SECURITY · ABUSE
注册接口计费反滥用
Reproduction
  1. 无 captchaToken 直接 curl -X POST /graphql 调用 register mutation；返回 200，token 与 refresh cookie 立即下发。
  2. 登录 Dashboard 后，Account Balance 显示 $5.00，UI 文案「Available for pay-as-you-go usage」。
  3. 同样的脚本可在分钟级注册任意多账号，每账号自动获得 $5 的可消费余额（无邮箱验证、无手机号、无 IP 限制）。
Impact
攻击者可在数十秒内创建数百个账号并集中消耗后端 LLM 资源，等于把成本直接转嫁给运营方。即使单账号 $5 看似不大，若上游 provider 为外采（OpenAI/Anthropic）则按真实定价结算，数千账号即数千美元成本。
Evidence
注册请求载荷包含 captchaToken: null，服务端未拒绝；Dashboard 截图显示 $5.00 余额。
Recommendation
  • 把 REGISTRATION_MODE 默认值改为 invite 或 verified-email；当前 docker-compose 默认 open 不应自动赠金。
  • 赠金逻辑需绑定邮箱+手机/支付凭据之一完成验证；可分阶段（注册立即 $0，验证邮箱 +$1，绑定支付 +$4）。
  • captcha 不能信任客户端字段，需在 register resolver 中强制校验 hCaptcha/Cloudflare Turnstile token。
  • 同 IP / 同设备指纹 / 同邮箱域名（gmail+ 后缀）做注册速率限制。
佐证
Critical C-02　访问态 JWT 写入 localStorage，任一 XSS 即可长期接管会话 SECURITY · AUTH
前端 ZustandJWTXSS Blast radius
Reproduction
登录后在控制台执行 localStorage.getItem('auth-storage')，返回包含完整 token（HS256 JWT）的 JSON 串： 
{"state":{"token":"eyJhbGciOiJIUzI1NiIsImtpZCI6ImxlZ2FjeSIsInR5cCI6IkpXVCJ9.eyJleHA…", …}}
该 JWT 直接用于所有 /graphql 与 /v1/* 调用。refresh token 在 Set-Cookie 中以 HttpOnly; Secure; SameSite=Lax 形式下发，但访问态 token 不是。
Impact
JWT 一旦泄漏，在 JWT_EXPIRES_IN=1h 内可完全冒充用户调用任意管理 API；管理员若被钓鱼则同样适用。RotateRefreshToken 强制 iat >= TokensInvalidatedAt 这条防御仅对 refresh 有效，攻击者无需 refresh — 直接拿 access token 即可。
Recommendation
  • 将 access token 也改为 HttpOnly cookie（与现有 refresh cookie 同源、SameSite=Lax，Path 仅限 /graphql 与 /v1），客户端无需读取，Apollo 关 credentials: 'include' 即可自带。
  • 如必须保留 bearer 模型，至少缩短 access token TTL 到 5–10 分钟，并强制每分钟悄静 refresh。
  • 在后端给所有写操作增加二次校验（最近一次密码 / TOTP），避免 token 被盗后任意提权。
  • 结合本报告 H-02 CSP worker-src 缺失 与 L-06 字段允许 HTML 标签，XSS 的暴露面并不为零。
佐证

  onboarding-storage: {"state":{"hasCompletedTour":true,…}}
  auth-storage:       {"state":{"token":"eyJ…(567 bytes)…"}}
sessionStorage:
  sentryReplaySession: {…}
document.cookie: ""           ← 注意访问态 token 不在 cookie，而在 localStorage
Critical C-03　普通用户 UI 主动调用 admin GraphQL 字段，并把「forbidden」原文 toast 给用户 AUTHZ · INFO LEAK
GraphQL @authUI 错误处理
Reproduction
以普通用户 weakpw@example.com 登录后进入 /playground，浏览器 toast 区出现 forbidden: admin access required。抓包发现请求体是 query Alerts($status:"active"){ alerts{…} }，命中后端 @auth(role: ADMIN) 拒绝。
Impact
  • UI 层把权限模型与字段名（alerts、targetType、alertType）直接打印给普通用户，泄漏后台模型。
  • 说明前端没有按用户角色拆查询；以 admin 路径上同款查询泛化到 user 路径 → 所有 user 都向后端发出至少一次注定失败的 admin 调用，造成无意义的 401/403 噪声、污染 audit log。
  • 错误处理链路有缺陷：本应在 Apollo errorLink 静默吞掉 FORBIDDEN + admin-only path 的错误，但实际 toast 出来。
Recommendation
  • 前端按 currentUser.role 条件加载查询（Apollo skip），admin-only 查询不应出现在普通用户 bundle。
  • Apollo 全局 errorLink 对 FORBIDDEN 走静默策略，仅 sentry 上报、不 toast。
  • 后端可考虑对未授权字段返回 null + warning 而非 error，配合 @auth 改为 nullable，避免侧信道泄漏字段存在性。

3. High 高优先级问题

High H-01　nginx 与 Go middleware 各自设置一套安全 Header，互相冲突 CONFIG · SECURITY HEADERS
Observed
所有 /graphql、/v1/*、/healthz 响应都同时返回两套 CSP / HSTS / Permissions-Policy / X-Frame-Options / X-XSS-Protection / Referrer-Policy / Cache-Control： 
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self';
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self' https://fonts.gstatic.com; connect-src 'self'

Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()
Permissions-Policy: camera=(), microphone=(), geolocation=()

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
Strict-Transport-Security: max-age=31536000; includeSubDomains

X-XSS-Protection: 0
X-XSS-Protection: 0

Cache-Control: no-store, no-cache, must-revalidate, private, proxy-revalidate
Cache-Control: no-cache, no-store, must-revalidate
Impact
  • CSP 重复：浏览器对多个 CSP 取交集（最严格），结果是 nginx 的 font-src https://fonts.gstatic.com 被 Go 的 font-src 'self' 吞掉；同理 frame-ancestors 'none' 与 nginx 的 X-Frame-Options: DENY 既定语义不冲突但语义冗余，会让审计/扫描器误报。
  • HSTS preload 标志仅在一份里有，提交 hstspreload.org 时会因「响应中有多条 HSTS」被拒。
  • Cache-Control 健康检查同时被两套规则覆写，nginx 的 no-cache 与 Go 的 no-store, …, proxy-revalidate，下游 LB 行为不可预测。
Recommendation
  1. 选定单一职责：让 Go 后端不再发安全 Header（关掉 SecurityHeaders() 中除 X-Content-Type-Options 之外的项），由 nginx 集中负责；或反过来——nginx 只透传 + 加 SPA cache 控制，Header 全部由后端发。
  2. 两份 CSP 合并为一份且包括 worker-src 'self' blob:（见 H-02）和 connect-src 的实际目标（langfuse / sentry / GraphQL ws）。
  3. HSTS 仅在 nginx 一处声明，且仅在 TLS-terminator 域返回，避免 preload 检测。
原始证据 
$ curl -sI http://localhost/graphql -X POST -H 'Content-Type: application/json' --data '{"query":"{__typename}"}'
HTTP/1.1 200 OK
…
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self';
…
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self' https://fonts.gstatic.com; connect-src 'self'

nginx 配置位于 web/nginx.conf，Go 中间件在 server/internal/api/middleware/security.go:104。

High H-02　CSP 未声明 worker-src，前端构造 blob: Worker 被全量阻断 CSP · BROKEN FEATURE
Observed
登录页 / dashboard / api-keys / settings 几乎每个路由都打印至少一次： 
[ERROR] Creating a worker from 'blob:http://localhost/…' violates the following CSP directive: "script-src 'self'". Note that 'worker-src' was not explicitly set, so 'script-src' is used as a fallback. The action has been blocked.   @ /assets/index-Cwve4tjX.js:3
Web Worker 是被 Sentry Replay 用来跑压缩 / 序列化，每次页面加载都失败。
Impact
Replay 在生产构建中完全停摆（无错误录像、无慢交互回放），但占用 bundle 体积、向 Sentry 上报失败、还污染控制台错误数。这影响线上稳定性观测，也意味着 vendor-sentry-DhV8gi6o.js 占用的 ~XXkB 是无效负载。
Recommendation
CSP 增加 worker-src 'self' blob:（仅当确实想保留 Sentry Replay）。否则在 vite build 配置中关闭 Replay integration，避免运行时无用代码加载。
High H-03　CSP connect-src='self' 阻断 Sentry 上报，但客户端仍在每次请求加 sentry baggage CSP · OBSERVABILITY
Observed
控制台报错（仅 admin 路由就累计 64 条）：
Refused to connect to http://localhost:9000/api/2/envelope/?sentry_version=7&sentry_key=c4ad6bd79b2990db75215e0a4b801910 because it violates the document's Content Security Policy.
同时所有 /v1/chat/completions 请求都仍然带：
baggage: sentry-environment=development,sentry-public_key=c4ad6bd79b2990db75215e0a4b801910,sentry-trace_id=…
sentry-trace: …-1
Impact
  • Sentry 在线上完全无效；研发误以为「Sentry 跑着」实际无任何 issue 落库。
  • 每个 fetch 多带 2 个 header（约 300 字节），针对 100 QPS 的高负载是 30 KB/s 无效开销。
  • Sentry DSN 中的 public key c4ad6bd79b2990db75215e0a4b801910 被打进静态 JS bundle，任何用户可读到（虽公开 key 设计上不属敏感，但建议生产用反代隧道而非直连）。
Recommendation
  1. 选定生产 Sentry 地址（https://sentry.example.com）并加入 CSP connect-src；本地开发用 self-hosted 时也要把 http://localhost:9000 写入。
  2. 构建时检测 VITE_SENTRY_DSN 是否为空，空则完全不挂 Sentry SDK；当前 docker-compose 把 VITE_SENTRY_DSN 作为 build arg 但仍生成 baggage。
  3. 对 baggage Header 加 propagation allowlist，只在被 trace 的接口加。
High H-04　注册表单写「最少 6 位」、后端要求 8 位，错误被 UI 静默吞掉 UX · VALIDATION
Reproduction
  1. 注册页 Password 字段下方文案："Minimum 6 characters."
  2. 填入 123456 → 提交。表单未跳转、未变色、未提示，按钮恢复默认状态。
  3. 抓包：服务端返回 {"errors":[{"message":"password must be at least 8 characters","extensions":{"code":"VALIDATION"}}]}。
  4. 普通用户的反应是「点了没反应，再点一次」——典型的死循环。
Impact
  • 违反「表单错误必须 inline 显示」的基本可用性约束。
  • 用户被引导用更弱的密码（6 位），即使后来侥幸用 8 位通过，平台仍把这种用户密码画像收住了。
  • 说明 Apollo errorLink + form 之间缺少绑定。
Recommendation
  • 统一密码策略：前端校验、Schema、后端 password_policy 三处只设一个常量并 import。
  • UI 引入 zxcvbn 强度条；后端最小长度从 8 提至 10 + 至少包含字母与数字。
  • 修复 register mutation 错误透传到表单，按字段映射 extensions.field。
对应代码 
// UI 文案
<p ref=e31>Minimum 6 characters.</p>

// 后端响应
{"errors":[{"message":"password must be at least 8 characters",
            "path":["register"], "extensions":{"code":"VALIDATION"}}],"data":null}
High H-05　创建 Webhook 失败时仅返回 “internal error”，用户无任何提示 SSRF · UX
Reproduction
Webhook 表单填入 http://llm-router-postgres:5432/ 后点击「Create Webhook」。
  • 服务端返回 {"errors":[{"message":"internal error [04d2fbd42ef55154d3863af7505132e8]","extensions":{"code":"INTERNAL","request_id":"…"}}]}。
  • 对话框不关闭，document.querySelectorAll('[role="status"]') 为空 → 没有任何 UI 提示。
Impact
  • 用户以为页面没响应。
  • SSRF 拒绝走「内部错误」分支说明验证错误没有走专门错误码。理论上 sanitize.ValidateWebhookURL 应该返回 VALIDATION + 字段，告诉用户 "URL must resolve to a public address"，但目前是 panic / err.Error 上抛。
  • 「internal error」会让支持人员误判为后端 bug 投入排查时间。
Recommendation
  • 所有 user-input-driven validation 错误统一映射成 extensions.code = "VALIDATION" + extensions.field。
  • 给 webhook URL 校验加专门错误：私网、loopback、保留 IP、非 https。
  • Apollo errorLink 对 INTERNAL 默认 toast 「Something went wrong (id: …)」，避免对话框失语。
High H-06　Dashboard / Subscription / Topup 余额三套真相 DATA CONSISTENCY · BILLING
Observed
  • Dashboard 首屏「Account Balance」= $5.00。
  • Subscription 首屏「Balance」= $0.00，1~2 秒后异步刷新为 $5.00。
  • "My Subscription → Current Plan = Free Tier" 同时显示 "Period Ends: --"。
Impact
数字财务字段在多个页面用不同 query 取不同 caching key，初始渲染显示 0给用户带来「我是不是没充上」的恐慌；这是付费转化路径上最忌讳的状态。
Recommendation
  • 把账户余额抽成单一 Apollo cache field（typePolicies.User.balance），所有页面读同一 reactive var。
  • 未拉取数据时显示 skeleton（animate-pulse 占位），不显示 $0.00。
  • 「Period Ends: --」改为「Not subscribed」或隐藏整个卡片。
High H-07　Payments disabled 时 Upgrade Now 仍可点，错误吞掉 UX · BILLING
Observed
点击 "Upgrade Now" 后服务端返回：
{"errors":[{"message":"payments are currently disabled","path":["createCheckoutSession"],"extensions":{"code":"VALIDATION"}}]}
但按钮不带 disabled 态、点击也不弹错误。
Impact
用户进入付费页期望升级，结果按钮看似无效——非常容易判定为 bug 并放弃。同时 admin 后台没有任何提示「当前 stripe/alipay/wechat 都关着」。
Recommendation
  • 用 GraphQL 查询 billingConfig.paymentsEnabled，UI 根据该字段决定是否渲染升级按钮，渲染为「Payments disabled — contact sales」。
  • admin Settings → Payment 增加横幅，提示当前未配置支付通道、点击跳转到 Stripe / Alipay / WeChat 配置页。
High H-08　Sentry DSN/public key 硬编码进 vite 静态产物，且与 self-host 实例不匹配 BUILD · SECRETS
Observed
vendor-sentry-DhV8gi6o.js 中包含 sentry_key=c4ad6bd79b2990db75215e0a4b801910 和 endpoint http://localhost:9000/api/2/envelope/。endpoint 显然来自构建时的开发环境 ENV，被打入了生产镜像。
Impact
  • Sentry public key 出现在前端是设计上可接受的，但 localhost:9000 这个 endpoint 一旦部署到任何 non-localhost 域就是死代码；目前镜像本身就是「错的」。
  • 说明 web/Dockerfile 的多阶段构建里 VITE_SENTRY_DSN 的来源未做空值短路。
Recommendation
改用 runtime config injection：在 web/public/runtime-config.js 由 nginx 在容器启动时 envsubst 生成，前端从 window.__RUNTIME_CONFIG__ 读取。同一个镜像可在任意环境跑。

MediumM-01　Onboarding tour 每次切页都重新打开，且 z-index 阻塞按钮点击UX · NAVIGATION
Reproduction
登录 → 出现 "Welcome to LLM Router Platform" 弹窗 → 点 X 关闭 → 点 sidebar API Keys → 弹窗又出现 → 该弹窗以 position:fixed; inset:0; z-index:100 包裹背景蒙板，覆盖在「Create your first API key」按钮上，导致 playwright 报：subtree intercepts pointer events。

Recommendation
tour 关闭状态写入 onboarding-storage.hasCompletedTour（截图证据显示该字段已存在但未被写入），点击 X 立即 setState。
MediumM-02　Playground STT / TTS 下拉里全是 chat 与 embedding 模型UX · DATA QUALITY
Observed
「STT Model」下拉包含 text-embedding-bge-m3、zai-org/glm-4.7-flash、google/gemma-4-31b……。这些不可能是 STT 模型，但下拉允许选择。

前端按 capabilities.input_modalities（/v1/models 已返回）过滤；TTS 同理。Provider sync 时把 whisper-* 等标 type=stt，kokoro-* 等标 type=tts。
MediumM-03　Playground TTFB 24s / 0 tok/s，但实际产出 1 tokenMETRICS · DIVISION-BY-ZERO
Observed
Playground 显示：TTFB 24423ms · Total 27298ms · 0 tok/s · Tokens: 12 in / 1 out = 13 · ~$0.0000。实际是 1 token / (27298-24423)/1000 ≈ 0.35 tok/s。
Recommendation
分母不为 0 时也至少保留 2 位有效数字；output_tokens / (total - ttfb)，当 total-ttfb < 100ms 显示「too fast to measure」。
MediumM-04　chat/completions 流推送 ~150 个空 delta 才出现首个 tokenPERFORMANCE · UPSTREAM PARITY
Observed
单条消息 "Say hi in one word." 的 SSE 抓包显示前 ~150 帧均为 {"choices":[{"delta":{}}]}，直到第 151 帧才出现 delta:{"content":"\n\n"}。看起来是后端把 LM Studio 上游的 think token 全部转发但 strip 了内容。
Impact
带宽浪费、TTFB 误判、客户端解析压力（typescript SDK 会一帧帧 emit event）。
Recommendation
在 server router 里把内容为空的 delta 合并/丢弃，或在 thinking 流末尾合并为单条 {"reasoning":"..."}（OpenAI o1 那样）。
MediumM-05　i18n 仅覆盖 sidebar，标题、正文、表单未翻译i18n
Observed
点 "中文" 按钮后：sidebar 全部变成「概览 / 数据分析 / 账号管理…」，但页面标题 Audit Logs / 主区描述 Review system security and access logs / 表格列名 / "showing 1 to 20" 等仍是英文。
Recommendation
把现有英文硬编码字符串移到 i18n/zh.json；建议先做覆盖率盘点（grep 直接含 ASCII 字母的 JSX 文本）。
MediumM-06　/admin/* 路由对 user 角色仅做客户端跳转，document.title 短暂闪烁AUTHZ · CLIENT-SIDE GUARD
Reproduction
普通用户访问 http://localhost/admin/users 会被重定向到 /api-keys，但跳转前一瞬间 document.title 已被设为 "Users - Router"，且 SPA 已加载对应 chunk。说明守卫位于 React useEffect / router beforeEnter 而非 SSR / nginx 层。
Recommendation
  • 在 React Router 的 loader 阶段同步校验 auth.role==='admin'，否则 throw redirect('/dashboard')。
  • chunk split 时把 admin 路由 lazy load，但确保 router guard 在 lazy import 前同步生效，避免提前拉 admin bundle。
MediumM-07　Admin Models 表全部 max_tokens=4096，与 /v1/models 自报 262144 不一致DATA QUALITY
Observed
  • GET /v1/models 返回 qwen/qwen3.6-35b-a3b 的 max_context_length: 262144。
  • Admin /admin/providers 中所有模型行 Max Tokens = 4,096。
说明 Provider sync 落库时把 max_tokens 当成了 OpenAI 兼容字段的「default response limit」而非「context window」。
Recommendation
区分两列：context_window 与 max_output_tokens。前端 Playground「Max Tokens」slider 上限应取后者。
MediumM-08　Admin Providers 把 whisper / embedding 模型混在 LLM 列表里DATA QUALITY
Observed
Models 表里同时出现 whisper-large-v3-turbo、text-embedding-bge-m3、text-embedding-nomic-embed-text-v1.5，列名仍然是 "Customer Price in/out"，对 embedding/audio 没有意义。
Recommendation
表格分组「Chat / Embedding / Audio (STT|TTS) / Image」，并按 capability 显示不同列。Provider catalog 数据模型应记录 type 与 capabilities 字段（其实 LM Studio 已返回，只是没存）。
MediumM-09　注册流程缺少邮箱验证、密码确认、CaptchaAUTH · ABUSE
Observed
注册仅 Name + Email + Password 三字段，无 confirm password、无邮箱验证、无 captcha；提交即登录。
Recommendation
参考 C-01：开放注册场景下需要至少 hCaptcha + 邮箱激活才能解锁付费/赠金。
MediumM-10　nginx 把 /metrics 直接 proxy 到 server，全靠后端 admin 鉴权DEFENSE IN DEPTH
Observed
nginx.conf 注释「/metrics is still protected by the backend's JWT + admin middleware」。当前实测确实需要 admin token，但缺少 nginx 层 IP allowlist / basic auth。如果未来某次后端误把 METRICS_ALLOW_UNAUTHENTICATED 设为 true，/metrics 直接对公开网开放。
Recommendation
  • 在 nginx 给 /metrics 加 allow 10.0.0.0/8; allow 172.16.0.0/12; allow 192.168.0.0/16; deny all;。
  • 把 prometheus 用的 metrics 端口隔离到内部 docker network，外部边缘不暴露。
MediumM-11　Recharts container 尺寸 -1,-1，admin dashboard 图表区空白UI · LAYOUT
Observed
控制台告警： 
The width(-1) and height(-1) of chart should be greater than 0,
       please check the style of container, or the props width(100%) and height(100%),
       or add a minWidth(0) or minHeight(256) or use aspect(undefined)…
出现在 admin dashboard "My Request Trend / My Spend Trend"。
Recommendation
给 ResponsiveContainer 父级显式 height（如 className="h-64"）或 aspect={2}；当前父级被 flex 计算为 0×0。

5. Low 低优先级问题

LowL-01　OPTIONS preflight 不回显 Access-Control-Allow-Origin，但允许所有方法CORS
Observed
$ curl -X OPTIONS http://localhost/graphql -H 'Origin: https://evil.example' …
HTTP/1.1 204 No Content
Access-Control-Allow-Headers: Origin, Content-Type, Authorization, X-API-Key, X-Request-Id, X-Trace-Id
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Max-Age: 86400
（注意：没有 Access-Control-Allow-Origin）
没有 Origin 反射在当前部署下意味着浏览器会拒绝跨域请求，所以并非可利用。但 Access-Control-Allow-Headers/Methods 已经准备好——一旦后端配置了通配 origin（CORS_ORIGINS=*），就会立刻打开。
Recommendation
显式声明仅在白名单 origin 时才回显这些 Header，避免运维误改 env 直接放开 CORS。
LowL-02　注册成功的 Set-Cookie 在 HTTP 下带 Secure，浏览器静默丢弃COOKIE
Observed
Set-Cookie: llm_router_refresh=eyJ…; Path=/; Max-Age=604800; HttpOnly; Secure; SameSite=Lax
本地 dev 用 http:// 跑，Chrome 会丢这个 cookie，refresh 流程在 dev 模式下完全失效，但开发者可能没意识到。
Recommendation
配置一项 COOKIE_SECURE=auto，根据 X-Forwarded-Proto 自动加，仅生产打开。
LowL-03　创建 API key 提示「不会再显示」，但 toast 关闭后 prefix 仍 visible，且全 key 直到 toast 关闭都在 DOM 里UX · SECRETS
Observed
提示文案："Please copy your API key now. You will not be able to see it again." 实际 prefix llm_7ffb... 长期可见，与文案语义不完全一致。同时密钥的全文 llm_7ffb62ab11b06cdef44acfd1bb36122bbecb69ddf70294c5316841d873f8a897 直到用户主动点 Dismiss 才被擦除——若用户开了 Sentry Replay（H-02 修好后），整 key 会被记录。
Recommendation
  • 提示语改为「Copy now; only the prefix will remain.」
  • 该 dialog 的 inner text 给 Sentry Replay 加 data-sentry-mask。
  • 30 秒后自动清空状态，避免下次开发者复现时键还在内存。
LowL-04　Profile 页面 H1 写「Settings」，导航 / 标签 / 标题写「My Profile」CONSISTENCY · COPY
Recommendation
统一为 "My Profile" 或 "Account Settings"，并改 document.title 与 H1 一致。
LowL-05　Provider catalogue 把开发自留模型当成产品模型展示CONTENT
Observed
Admin Providers / Playground 都列出 qwen3.5-35b-a3b-uncensored-hauhaucs-aggressive。这类带「uncensored / aggressive」的模型名出现在生产 catalogue 会带来法务与合规问题。
Recommendation
Provider sync 默认 active=false，由 admin 手工 enable 才进 user-facing 列表；或加 nameRegex 黑名单。
LowL-06　API key Name 字段允许 HTML 标签XSS DEFENSE
Observed
创建 key 时 Name <script>alert('xss')</script>audit key 保存成功，列表中以 React text node 输出（不执行），但下拉框 (<option>) 与表格 cell 都把 tag 作为纯文本展示。
Impact
当前安全（React + CSP 双保险）。但是一旦：1) 有人未来在某条路径用未转义 HTML 渲染该字段；或 2) 把 name 导出 CSV / PDF（PDF generator 不一定 escape） — 立刻就是 stored XSS。
Recommendation
Schema 层加正则 ^[\w\s\-\.（）()]{1,64}$。简单粗暴避免后患。
LowL-07　/healthz 返回了两条 Cache-Control，值互相冲突HEADERS
Observed
Cache-Control: no-store, no-cache, must-revalidate, private, proxy-revalidate    ← Go
Cache-Control: no-cache, no-store, must-revalidate                                ← nginx
实际效果浏览器只看第一条；但 LB 可能会以最严格的为准。前后端配置漂移信号。
Recommendation
解决 H-01 即可。

6. Informational

InfoI-01　注册响应 Set-Cookie 内嵌可 base64-decode 的 JWT iat/subINFO LEAK
Observed
refresh JWT 可被任意持有 cookie 的中间代理解码（HS256 仅签名不加密），其中含 sub=用户 UUID、iat=注册时间戳。
Recommendation
设计上正常，但若产品对「用户 ID 不外露」有要求，可考虑用 opaque random refresh token + DB 反查。
InfoI-02　Sentry baggage 在 CSP 拒绝后仍随每次 fetch 发出OBSERVABILITY · OVERHEAD
Recommendation
见 H-03，构建期决定是否注入 SDK。
InfoI-03　Langfuse self-host UI 经 nginx auth_request 校验 Authorization，但实际打到 /healthzINTEGRATION
Observed
nginx 把 /langfuse/ 接 auth_request /auth/verify → proxy_pass /healthz。当前 /healthz 不要求 auth，所以 auth_request 永远 200，实际并未保护 langfuse；同时上游 langfuse-server 没在 docker-compose 默认 profile 启动，访问 /langfuse/ 返回 504。
Recommendation
将 /auth/verify 改为真实的 token 校验子路由（/internal/auth），并要求 Authorization Header；当前实现是无意义的 placeholder。
